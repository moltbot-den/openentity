## Notes

1. Recovery by a platform attestation (spec 9.2 table, "domain, wallet or platform attestation"). The registry accepts a proof by a verified `domain` or `wallet` alias that the previous EID's signed document lists, and no other (R:635, row 4a). A platform attestation has no key of its own to sign a link with, and any DID may issue an `identity` attestation (spec 8.4), so accepting one would let anyone take over an entity by attesting to it first. Narrower than the spec is the safe side; widening it needs a rule that ties the signer to a verified `platform` alias and is a spec decision, not a code fix.
2. Recovery by a wallet alias signing the link with a real EIP-712 or EIP-191 signature is covered end to end by the alias verification tests plus the signer comparison (R:636-637); the registry tests for recovery pin the rejection paths and the domain path with a real signature.
3. Takedown policy (row 52) is a published page, not registry behavior; there is no machine check for it. Everything the policy depends on (the `suppressed` flag and its effect on listings) is row 51.
4. Rows marked `n/a` are statements for humans (no secrets in entries, "SHOULD bind an alias"); nothing in code can decide them.
